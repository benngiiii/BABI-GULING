## 3. Review Findings and Suggested Improvements

### Finding 1: Clarify the Relationship Between Model Evaluation and the Test Set

**Severity:** High

**Location:** Sections 3.3, 3.5, 3.9, and 3.10

**Issue:**

The chapter correctly explains that a test set should remain untouched during model development. However, Section 3.10 presents a workflow in which the team evaluates a model, improves the data or algorithm if the result is insufficient, and repeats the process.

This can suggest that the test set is repeatedly used to guide development. Repeatedly adjusting a model based on test results can cause information from the test set to influence development, making the final performance estimate less reliable.

**Suggested Improvement:**

Clarify that the validation set should guide model selection and iterative improvements. The test set should be reserved for final evaluation after development decisions have been completed.

If the model is revised based on the final test results, a separate untouched test set may be needed for an unbiased final evaluation.

### Finding 2: Clarify the Simplified Explanation of LLM Embeddings

**Severity:** Medium

**Location:** Section 3.7, Step 1: Tokens and Embeddings

**Issue:**

The statement that tokens with similar meanings end up with similar numbers is a useful introduction, but it may imply that every embedding directly represents a token's meaning in a simple, fixed way.

Embeddings are numerical representations learned by the model. Their relationships can reflect linguistic patterns and contextual information, but they do not guarantee that semantically similar tokens will always have nearby representations in every relevant sense.

**Suggested Improvement:**

Clarify that embeddings represent tokens as numerical vectors and that training helps the model learn useful relationships between these representations.

A short note can explain that the representation of a token is not a complete dictionary definition of its meaning.

### Finding 3: Distinguish Evaluation Metrics from Deployment Decisions

**Severity:** Medium

**Location:** Sections 3.9 and 3.10

**Issue:**

The chapter provides useful examples of accuracy, precision, recall, and F1. However, the spam-filter case study presents 80% recall and 89% precision as evaluation results and then describes improvement until the model is acceptable.

The example does not explicitly explain how the team determines what counts as acceptable performance or whether the decision threshold is appropriate for the intended application.

**Suggested Improvement:**

Add a brief explanation that acceptable performance depends on the problem, the cost of different errors, and the application's requirements.

For example, a spam filter may need to balance catching spam against the risk of incorrectly blocking important emails. Evaluation metrics should inform the deployment decision rather than determine it automatically.

### Finding 4: Specify an Accessible Tool for Activity D

**Severity:** Low

**Location:** Section 3.17, Activity D

**Issue:**

The activity asks learners to visit a free, browser-based interactive tool for training a small classifier but does not identify a particular tool.

This leaves beginners to find an appropriate resource themselves and makes the activity less immediately actionable.

**Suggested Improvement:**

Provide one suitable tool with a verified link and a short instruction explaining how to use it. If the activity is optional and the team prefers not to add a specific resource, retain it as an exploratory activity but make clear that learners must locate a suitable tool themselves.

### Finding 5: Verify External References and Time-Sensitive Claims

**Severity:** Medium

**Location:** Section 3.18 and claims throughout the chapter

**Issue:**

The chapter contains a useful range of references, including Google for Developers, academic papers, and educational resources. However, the actual links and their support for the associated claims have not been independently verified during this review.

The reference to the *AI Index Report 2026* and the statement that links were last checked on 23 October 2026 also require confirmation before publication.

**Suggested Improvement:**

Verify that each URL resolves to the intended resource and supports the associated claim. Confirm the cited report edition and update the last-checked statement only after the links have actually been checked.

### Finding 6: Recheck the Two Outstanding Findings from QR-003-I03

**Severity:** High

**Location:** Sections 3.4 and 3.8

**Issue:**

The previous review identified two technical issues:

* Section 3.8 separates inference-time improvements from training-based improvements.

However, because the actual repository file was not independently inspected, these changes cannot be confirmed in the committed version.

**Suggested Improvement:**

Verify that these corrections are present in the actual Markdown file in the repository. If confirmed, mark these two previous findings as resolved in the review history.
